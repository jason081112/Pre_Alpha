# 规划：让 C 端用户自己造一个人物

目标：用户不用命令行、不写 YAML，就能从零或从聊天记录造出一个能聊、像样、可编辑的人格。

本文件只做规划与依赖约定，实现散在 #83–#86 与既有 #42 / #46 / #47 / #49 / #72。

## 现状差距（2026-10-30 核查）

| 能力 | 现状 | 缺口 |
|---|---|---|
| 人格列表 | OpenHer `GET /api/personas` 只读 | 没有"谁的人格"、没有元数据 |
| 创建人格 | 只能往 `persona/personas/` 放目录 | 无 API、无校验、无版本 |
| 编辑人格 | 只能手改 `SOUL.md` | 无 diff、无回滚、易改坏 |
| 删除人格 | 只能删目录 | 无回收站、无级联（状态/记忆残留） |
| 多用户隔离 | 全局共享 | 用户 A 的人格用户 B 可见 |
| 蒸馏生成 | 链路到 #32（只身份字段） | 正文四槽、种子、驱动参数未接 |
| 用户入口 | 无 | `alpha profile2soul`（#42）是占位 |

## 里程碑

**M1 · 能造（最小闭环）**

- #83 + #84 起步：POST 创建、GET 列表、DELETE 软删除，单人单机可用
- #85 CLI 先做（无 UI 也能验证流程）
- 验收：命令行造一个内置 fork，改名字与一条口头禅，聊 3 轮不报错

**M2 · 能像**

- #33–#38 完成正文与数值映射
- #35 口头禅进 `style_memory`，#36 事实进 FTS5
- #86 体检把"缺什么"讲清楚
- 验收：#44 的 20 轮对话里，口头禅至少命中 2 次、冲突反应符合 `conflict.repair`

**M3 · 能用（C 端）**

- #85 Web/PWA 三步向导 + #86 保存前体检
- #84 配额与回收站、#73 加密、#74 导出、#75 注销
- 验收：新用户从注册到"造出第一个能聊的人物"≤ 10 分钟，全程不碰命令行

## 验收总纲（什么算"实现了"）

1. **零技术门槛**：不写 YAML、不碰文件系统、不改代码，能完成创建与编辑。
2. **诚实**：材料不足时显示「未提供」，推断必须写依据，引擎的默认值回落必须告知。
3. **可回滚**：任何编辑都有版本，能看 diff、能撤销。
4. **有边界**：跨用户不可见，删除可恢复，配额有上限。
5. **可解释**：体检报告能回答"为什么不像"——缺正文、缺口头禅、缺驱动参数。
