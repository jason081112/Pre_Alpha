# ADR-0001 · 部署形态：引擎统一云端 + Web/PWA 优先

- **状态**：Accepted
- **日期**：2026-10-19
- **关联**：`docs/architecture.md` 部署架构方向；P0-7 / P0-8 结论修订；看板 #66–#78

---

## 背景

P0 阶段最初以「OpenHer 后端跑在用户手机（Termux）」为前提做调研，P0-7 因此把「Termux 磁盘仅剩 555 MB」列为 P1 首要阻塞项，P0-8 把「单一 OpenRouter」列为 P1 唯一 provider。

该前提在产品化视角下不成立：

1. **手机不能长期开机**——陪伴型 AI 的核心是主动消息与持续在线，端侧本地进程无法满足。
2. **产品要推向 C 端用户**——不可能要求每个用户自己装 Python、跑 Termux、维护环境。
3. **磁盘 / 网络约束**——Termux 磁盘紧张、github.com 连通不稳，工程上不可持续。

## 决策

**引擎（OpenHer）统一云端运行，客户端 Web/PWA 优先；上游核心代码不改，外围加壳。**

```
客户端层   Web/PWA（先做） · [APK 搁置] · [微信桥 可选]
              │ HTTPS + WebSocket
接入层     认证 / 会话 / 限流 / OpenAI 兼容端点
              │
引擎层     OpenHer 按需加载状态 → 跑一轮 → 持久化（上游基本不改）
              │ + 主动消息调度器（独立轻量循环 = 陪伴的灵魂）
              │
数据层     agent/metabolism 状态 · 记忆(SQLite FTS5/每用户) · 账号/订阅/BYOK
```

## 为什么是「加壳」而不是改 OpenHer

- 后端 API 已完备：REST（`/api/chat`、`/api/personas`、`/api/chat/history`…）+ WebSocket `/ws/chat`（含主动消息推送）
- 已有 `state_store`（CAS 版本 + 状态持久化）→ 引擎状态可外置，支持多用户按需加载
- 上游为 Apache-2.0，加壳可避免维护 fork 的分叉成本

## 隐私定位（修订原「数据不出设备」红线）

| | 原红线 | 修订后 |
|---|---|---|
| 云端模式 | 不支持 | 传输加密 + 静态加密 + 不训练 + 不分享 + 可导出可删除 + 首次启动明示 |
| 本地模式 | 唯一形态 | 保留为**未来的第二个 Store 实现**，当前不实现（架构不锁死） |

对应任务：#73 静态加密、#74 数据导出、#75 账号注销、#76 隐私政策明示、#77 不训练承诺落地。

## 连带修订

- **P0-7**：Termux 磁盘 555 MB 由 🔴 P1 阻塞 **降级** 为 🟢；Termux 仅作开发环境。
- **P0-8**：LLM provider 由「单一 OpenRouter」改为 **多 provider + BYOK 双轨**（#70 路由层、#71 Key 管理）。
- **搁置项**（归属后续阶段）：Android APK、双引擎、多租户实现细节、订阅 / 计费实现、微信桥接入。

## 后果

**正面**
- 主动消息、多用户、跨设备可用；用户零安装成本
- 部署与扩容路径清晰（#78 容器化）

**负面 / 待解**
- 对话内容经过云端 → 必须用技术（加密）+ 制度（政策、不训练条款）补偿
- 单用户状态加载 / 落盘引入延迟 → 需 #69 验证可行性与瓶颈
- 平台 Key 模式有推理成本 → 靠订阅或额度和 BYOK 双轨覆盖

## 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 全本地（用户设备跑引擎） | 无法主动消息；C 端无法要求用户配环境；手机资源不足 |
| 混合（本地蒸馏 + 云端对话） | 依然要云端常驻，复杂度更高，收益不明确；蒸馏产物仍需上传 |
| 纯 fork 改造上游 | 与上游分叉，后续升级成本高，违背「加壳」原则 |
