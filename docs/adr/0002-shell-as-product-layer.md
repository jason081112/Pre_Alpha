# ADR-0002 · 对外只暴露 `shell/`，引擎 `main.py` 保持上游原样

- **状态**：Accepted
- **日期**：2026-11-05
- **关联**：ADR-0001（云端部署）、#45（路由清单）、#46（Web 聊天页）、#47（CLI chat）

---

## 背景

P1 阶段我们在 `shell/` 里建了一整套产品能力：认证（邮箱/邀请码 + refresh token）、
按 `user_id` 的会话隔离、限流配额（#67）、多 provider 路由（#70）、BYOK 密钥管理（#71）、
OpenAI 兼容端点（#68）。

同时 `vendor/OpenHer/main.py`（1573 行、17 个路由）也能跑起来、能对话。

问题：**两套并存且不互通。**

| | `main.py` | `shell/` |
|---|---|---|
| 能否对话 | 能 | 能（但引擎在另一个进程里） |
| 认证 | 无（`client_id` 是 localStorage UUID，可伪造） | 有 |
| 多用户隔离 | 无（全局 `active_sessions`） | 有 |
| 限流配额 | 无 | 有 |
| OpenAI 兼容 | 无 | 有 |
| 流式 | WS 分块 | 未接 |

不清这个，P4 写出来的 Web 页不知道连哪个端口。

## 决策

**`shell/` 是唯一对外入口；`main.py` 作为内部服务，保持上游原样不改。**

```text
浏览器 / CLI / OpenAI SDK
        │ HTTPS + WebSocket
        ▼
┌──────────────────────────────┐
│ shell/  （产品层，我方维护）   │
│ · 认证 / 会话隔离 / 限流       │
│ · OpenAI 兼容 /v1/chat/...    │
│ · 人格 CRUD（#83）            │
│ · 代理：转发到引擎并注入上下文  │
└──────────────┬───────────────┘
               │ 内部 HTTP / 同进程调用
               ▼
┌──────────────────────────────┐
│ vendor/OpenHer/main.py       │
│ （上游，保持原样，不 fork 修改）│
│ · Genome 引擎 / critic / 记忆 │
└──────────────────────────────┘
```

## 为什么不是「把引擎嵌进 shell/」

嵌入的收益是少一跳、少一个进程。但代价是：

1. **上游升级要手工合并**。OpenHer 还在迭代（v0.5.0，Genome v10），一旦把
   `main.py` 的启动逻辑拆进 `shell/`，每次上游更新都要重新对一遍。
2. **认证和引擎会互相污染**。目前 `main.py` 是「谁连都能用」，我们靠外层挡。
   嵌进去之后，两件事会混在同一个进程的全局状态里（`active_sessions`、
   `persona_loader` 都是模块级单例）。
3. **P1 的成果要推翻**。认证、限流、OpenAI 兼容都已按「包一层」的思路做完，
   嵌进去等于重做。

代价（多一跳）是可控的：内网 / 同机 localhost 调用，延迟在毫秒级，相对模型推理
（秒级）可以忽略。

## 保留上游的两个设计

### 1. 打字防抖

`main.py` 的 WS 端点里有：

```python
DEBOUNCE_GRACE_SEC = 2.0      # 光标离开输入框后等 2 秒
DEBOUNCE_FALLBACK_SEC = 3.0   # 无打字信号时等 3 秒
```

用户连发几条消息时先缓冲，合并成一轮再处理。

**为什么必须保留**：真实聊天里人确实会「说一句、补一句」。逐条处理会让她的回复错位——
你发了「今天特别累」，她回「怎么了」；你接着补充「还下雨了」，她又回一句「那你早点回」。
变成自问自答式的机械应答。

**代理层要做的**：`shell/` 转发时也要维持这个语义，不能因为多了一层就把缓冲打散。

### 2. 流式分块

WS 的 `chat_chunk` 逐段推，不是等全文生成完。

**为什么必须保留**：陪伴场景对首字延迟极敏感。等 8 秒出现一整段，和 1 秒出现第一个词，
体验差一个量级。

上游**没有 SSE**，流式只有 WebSocket 一条路。所以代理层要支持 WS 透传，而不是把
流式转成一次性响应。

## 后果

**正面**

- `main.py` 保持上游原样，升级只需替换 vendor、跑 `fetch_openher.sh`
- 认证、隔离、限流只在一处（`shell/`），不会出现两套规则
- 对外契约稳定：前端只认 `shell/` 的端点，引擎换实现不影响客户端

**负面**

- 多一跳网络（内网，毫秒级）
- WS 透传需要额外实现（不是简单的 HTTP 反向代理）
- `shell/` 要维护「引擎返回什么 → 对客户端返回什么」的映射层（例如
  `reply` → `response`、`segments` 拆分）

**必须注意**

- `/api/demo/inject` 是上游的演示后门，**不能**透传到外网
- 上游 `/api/personas` 只读，人格 CRUD 必须走 `shell/` 的 #83 端点，两者不要混用
- 上游 `client_id` 不是认证，代理层要用真实 `user_id` 覆盖，不能把它当身份

## 实施顺序

1. `shell/` 增加引擎客户端（HTTP + WS 两种）
2. 认证后的请求 → 注入 `user_id` → 转发引擎 → 映射响应
3. WS 透传保留防抖与分块语义
4. #46 Web 页、#47 CLI 都只连 `shell/`
